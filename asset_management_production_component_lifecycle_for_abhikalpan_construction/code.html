The Multi-Story Lifecycle Problem

When Abhikalpan builds a multi-story residential project like IPO-023, there are over 10,000 distinct aluminium profiles. Each one is custom cut to millimeter tolerances. 10 // RELATIONAL TOPOLOGY

THE UI IS ONLY THE SURFACE.

A slick frontend cannot save a corrupted database. The core architectural achievement was an airtight relational schema that makes dangling records physically impossible.

RELATIONAL SCHEMA & FOREIGN KEY TREE 
[USERS] ──< (created_by) ── [PROJECTS] ──< [COMPONENTS] ──< [PRODUCTION_LOGS]
                                  │               │
                                  │               ├─> [PALLETS] ──< [HANDOVER_RECORDS]
                                  │               │
                                  └───────────────┴─> [AUDIT_LOGS (Immutable Append-Only)]
                                                  │
                                                  └─> [FABTRACK_STAGES]
TABLE: components
• id: BIGSERIAL (PK)
• serial_no: VARCHAR(64) UNIQUE
• project_id: INT (FK -> projects)
• pallet_id: INT (FK -> pallets, NULL)
• status: component_status_enum
• flat_id: VARCHAR(32)
TABLE: pallets
• id: BIGSERIAL (PK)
• qr_code_hash: VARCHAR(128)
• project_id: INT (FK)
• qc_status: qc_enum
• sealed_by: INT (FK -> users)
• dispatch_time: TIMESTAMP WITH TZ
TABLE: audit_logs
• id: UUID (PK)
• entity_id: BIGINT
• previous_state: JSONB
• new_state: JSONB
• actor_id: INT (FK)
• ip_hash: VARCHAR(64)
ARCHITECTURAL LESSON: “The hard part of this platform wasn’t displaying the data nicely. The hard part was keeping the data mathematically correct while 25 operators on spotty Wi-Fi changed it simultaneously.”
